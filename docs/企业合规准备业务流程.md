# 企业合规准备业务流程（对应左侧产品线）

> 本文说明：公司在本平台做 **SOC 2 合规准备** 时，从开通到出结果的完整流程，并与当前界面菜单/页面对齐。  
> 这不是会计师事务所正式出审计报告的那条产品线。

---

## 1. 一句话说明

公司付钱开通服务 → 建项目、加人 → 按条款要材料 → 整理风险与控制措施 → 定检查范围并检查 → 找缺口并整改 → 看准备结果；重要操作全程留痕。

---

## 2. 总流程图

```text
登录 / 注册
    ↓
选产品、选覆盖范围、选评估深度、付款开通
    ↓
建项目（项目总览） + 配置人员（权限管理）
    ↓
请求总单（Request master）→ 单条请求（Request individual）要材料、交材料、审材料
    ↓
控制表（Control table）整理风险与控制措施
    ↓
控制测试（定检查范围并执行检查）
    ↓
差距分析（找缺口、催整改）
    ↓
准备结果 / 得分
    ↓
操作日志（全程可查）
```

## 3. 分步说明（每步对应哪个画面）

### 步骤 0：进系统

| 做什么 | 对应画面 | 说明 |
|--------|----------|------|
| 注册账号 | 注册页 | 可填邀请码，加入某公司/项目 |
| 登录 | 登录页 | 进入后按是否已购服务走不同入口 |
| 改个人/公司资料 | 个人中心 / 公司资料 | 头像入口常见 |

---

### 步骤 1：买服务、开通能力

| 做什么 | 对应画面 | 说明 |
|--------|----------|------|
| 看有哪些合规产品 | 选产品页 | 当前主推 SOC 2 |
| 选覆盖范围、评估深度、看价格 | 购买 / 定价页 | 覆盖范围例如：安全、可用性、保密性等；评估深度有浅/深两种 |
| 下单支付 | 结账 / 支付页 | 付成功后账号开通对应能力 |

**业务含义：** 买了哪些范围，后面「要材料、控制表」原则上只处理这些范围。

---

### 步骤 2：建项目、配人

| 做什么 | 对应画面（侧栏常见名） | 说明 |
|--------|------------------------|------|
| 新建/查看/进入项目 | **项目总览**（Project overview） | 一次合规准备对应一个项目 |
| 编辑项目基本信息 | 项目详情 / 项目设置 | 名称、时间、说明等 |
| 给项目配置角色与人员 | **权限管理**（Access management） | 表格：每个项目一行，各角色列显示已分配的人 |
| 邀请同事进项目 | 权限管理里的「邀请」 | 生成邀请码 |
| 已有账号输入邀请码入项 | 权限管理里的「邀请码」弹窗 | 输入码后确认加入 |

**常见角色（白话）：**

- 管理员：公司/项目最高管理
- 项目负责人：对这个项目总负责
- 文档负责人：材料收集相关
- 普通用户：协作交材料等
- 一级 / 二级经理：管理层级协作

---

### 步骤 3：要材料（证据收集）

| 做什么 | 对应画面 | 说明 |
|--------|----------|------|
| 看本项目下有哪些「总任务单」 | **请求总单**（Request master） | 一轮材料收集的总入口；总单由用户新建（如「汽轮机厂第一季度询问」） |
| 新建总任务单、改状态 | 请求总单列表 / 表单 | 总单只是任务包名称，与公司行业无关 |
| 进入总单后生成材料清单 | 单条请求页的「生成」 | **按公司已购套餐范围**，从平台标准条款库灌入；同一条款下多行材料要求会生成多行 |
| 看总单下每一条要交的材料 | **单条请求**（Request individual）列表 | 生成后的清单；名称由系统自动给唯一键 |
| 打开某一条：指定交材料人、上传附件、发送、审阅 | 单条请求详情 / 侧栏 | 用户主要做执行，一般不自己发明标准条款 |
| （少数）补一条临时材料任务 | 单条请求「新建」 | 跟进项；标准条款仍以生成为主 |

**重要约定：**

- 生成哪些条款：**只看已购套餐覆盖范围**，与项目名称、公司行业无关。
- 总单：用户建；清单内容：系统灌；用户：交材料、审材料。

**可以这样记：**

- **请求总单** = 这一季/这一轮的「材料收集总表」
- **单条请求** = 总表里的「每一行要交的东西」

**给非专业同事的白话解释：**

- 买了哪个范围（例如 **Security**），系统就会按这个范围生成对应的标准条款任务。
- 用户不是从全库里自己随便挑几条上传，而是先由系统生成清单，再按清单去交证据。
- 这些证据通常是制度、流程、截图、会议纪要、报表、审批记录等，用来证明「这条要求公司确实有在做」。

**当前系统里，步骤 3 更准确的理解是：**

1. 先买套餐，确定覆盖范围（如 Security）。
2. 在 Request master 下点 **生成**，系统按已购范围把标准条款灌成一批 Individual 任务。
3. 用户在每条任务里指定交材料人、上传证据、发送、审阅。
4. send 后，AI 目前主要返回证据审阅结果（如 `not right` / `need attention` / `all good`），不是自动给公司下风险结论。

---

### 步骤 4：整理风险与控制措施

| 做什么 | 对应画面 | 说明 |
|--------|----------|------|
| 维护风险—控制措施对应关系 | **控制表**（Control table） | 常见还有人工维护、系统生成草稿、确认定稿等子页面 |
| 指定某条措施的负责人 / 复核人 | 控制表相关表单 | 后面差距分析会找到这些人来确认 |

**业务含义：** 前面要来的材料，会支撑「我们用什么措施管什么风险」这张大表。

**更白话地说，这一步主要回答 3 个问题：**

1. 我们公司在这块可能有什么风险？
2. 我们准备用什么控制措施去管？
3. 这件事谁负责、谁复核？

**它和步骤 3 的区别：**

- **步骤 3** 重点是「交证据」：系统按条款生成任务，用户上传材料。
- **步骤 4** 重点是「整理管理逻辑」：把风险、控制措施、责任人整理成控制表。
- 两步常常围绕同一批安全条款，但不是同一张表，也不是同一个动作。

**最容易混淆的一点：**

- 买了 Security，不等于系统已经替公司完整定义好了「本公司的全部风险台账」。
- 购买时定义好的，更多是「要按哪套标准准备、会生成哪些条款任务、通常要交哪些材料」。
- 控制表则是在这些条款任务基础上，进一步整理成「本公司怎么管、谁负责」的表。

**当前系统里，步骤 4 的数据主要从哪里来：**

1. **从步骤 3 同步草稿**：Request individual 新建、更新、上传附件等操作后，会同步出控制表草稿。
2. **人工维护**：用户可在控制表里补充或修改风险描述、控制措施、负责人、复核人。
3. **Excel / AI 辅助**：系统也支持导入或 AI 生成 / 补全，但仍需要人工确认。

**当前系统的一个重要现实：**

- 控制表里的草稿，常常是由步骤 3 的任务同步出来的，所以数量上看起来会比较像「一条任务对应一条控制表草稿」。
- 但系统目前并不是读取你上传的 10 份文件内容后，自动判断出 10 条风险。
- 现在更接近于：**任务同步成草稿，证据用于支撑，风险和控制措施仍需要人来补全和确认。**

---

### 步骤 5：定检查范围并做检查

| 做什么 | 对应画面 | 说明 |
|--------|----------|------|
| 决定这次要查哪些控制措施 | 控制测试 / 测试计划相关页 | 相当于定「考试范围」 |
| 执行检查、记录结果 | **控制测试**（Control Testing） | 做得怎样、有没有问题 |

---

### 步骤 6：找缺口、整改

| 做什么 | 对应画面 | 说明 |
|--------|----------|------|
| 汇总缺材料、措施不到位等问题 | **差距分析**（Gap Analysis） | 看缺口清单 |
| 负责人确认并跟进整改 | 差距分析相关操作 | 关注：什么时候、谁、要改什么 |

---

### 步骤 7：看准备结果

| 做什么 | 对应画面 | 说明 |
|--------|----------|------|
| 查看本次合规准备整体得分/结论 | **准备结果 / 得分**（Passing Scores） | 偏「自己准备得怎么样」，不是会计师盖章报告 |

---

### 步骤 8：全程留痕

| 做什么 | 对应画面 | 说明 |
|--------|----------|------|
| 查谁、何时、改了什么 | **操作日志**（Operation Log） | 对应流程图底部的全程追踪要求 |

## 4. 侧栏菜单与流程步骤对照（快速查）

以下名称以当前产品界面常见文案为准（截图侧栏）：

| 侧栏 / 页面 | 对应上面第几步 | 一句话 |
|-------------|---------------|--------|
| 登录 / 注册 / 个人中心 | 步骤 0 | 进系统、改资料 |
| 选产品 / 购买 / 支付 | 步骤 1 | 付钱开通 |
| Project overview（项目总览） | 步骤 2 | 建项目、进项目 |
| Access management（权限管理） | 步骤 2 | 给项目配人、邀请码 |
| Request master（请求总单） | 步骤 3 | 材料收集总任务 |
| Request individual（单条请求） | 步骤 3 | 每一条材料任务 |
| Control table（控制表） | 步骤 4 | 风险与控制措施 |
| Control Testing（控制测试） | 步骤 5 | 定范围并检查 |
| Gap Analysis（差距分析） | 步骤 6 | 找缺口、整改 |
| Passing Scores（准备结果） | 步骤 7 | 看准备结论 |
| Operation Log（操作日志） | 步骤 8 | 留痕查询 |

**当前菜单使用建议（结合现有界面问题）：**

- `Project overview` 更适合作为默认入口。
- `Access management`、`Request master`、`Control table`、`Control Testing`、`Gap Analysis`、`Passing Scores` 这些都更像**项目内页面**，最好先进入某个项目后再看。
- 如果还没有进入具体项目，就直接点这些页面，当前实现里容易因为缺少项目上下文而报错。
- 多项目场景下，建议前端后续做成「先选项目，再进入项目内菜单」的结构，这样会比把所有项目内页面直接长期挂在侧栏里更清楚。

## 5. 典型使用故事（串起来）

1. 管理员注册登录，购买 SOC 2，选好覆盖范围和评估深度并付款。  
2. 在 **项目总览** 新建项目「2026 合规准备」。  
3. 在 **权限管理** 给项目配负责人、文档负责人，并用邀请码拉同事进来。  
4. 进入 **请求总单** 新建「第一季度询问」→ 进入后点 **生成**（按已购范围灌标准材料清单）→ 在 **单条请求** 里让同事交材料、负责人审。  
5. 在 **控制表** 整理风险与控制措施，指定负责人。  
6. 做 **控制测试**，再在 **差距分析** 里补缺口。  
7. 打开 **准备结果** 看整体情况；需要时到 **操作日志** 查变更记录。

## 6. 和「右侧正式审计产品」的区别（避免混淆）

| | 本流程（左侧，当前主做） | 右侧（暂不展开） |
|--|-------------------------|------------------|
| 谁用 | 企业自己做准备 | 会计师事务所 |
| 终点 | 准备结果 / 得分 | 正式审计报告 |
| 怎么卖 | 按标准、覆盖范围、评估深度套餐 | 按委托项目、用户数等 |
